# Preregistration: shared-runtime ARC-3 transfer

Frozen before implementation on 2026-09-08.

## Immutable inputs

- Shared replay-gated runtime: `4f03be5acc34ce23775c19cd7f291ba001bf8b67`.
- Frozen ARC-3 parameterized harness: `68e37033f3ae1e86e992dfe8d982aef9133612aa`.
- Public ARC toolkit repository: `arcprize/ARC-AGI` at
  `f12822c4d550121c35a275008d964afbbed47d2f`.
- Toolkit package: `arc-agi==0.9.9`.
- Public second game: `bt33-a7c3f9d18b4e`.

The prior ARC checkpoint already records a successful bounded result on this
game. Therefore this is not an outcome-blind discovery claim. The new question
is architectural: can the option generated by that frozen source-blind harness
be selected and replay-gated by the shared developmental implementation before
it is retained and deployed?

## Frozen mechanism

1. Build the bounded parameterized action alphabet only from the public action
   space and public image dimensions.
2. Run the frozen option-compositional discovery procedure. No successful
   action sequence, object location, game rule, or source file enters the new
   adapter.
3. Take the first option witnessed by external level progress. Select a sham
   from actually executed zero-progress training evidence, not from a supplied
   sequence.
4. On fresh environments, execute the cold primitive baseline, the sham, and
   the acquired candidate. These are pre-promotion observations.
5. Generate a Lean instance whose candidate tags are the observed sham and
   acquired programs. `SynthesisCore.develop` must select the acquired tag from
   the observed developer-behaviour residual, and
   `SynthesisCore.promoteIfReplayAdequate` must recompute an empty replay
   residual for that exact tag. A forged failed-replay quotient must be refused.
6. Retain the exact candidate only after Lean exits successfully. A fresh warm
   deployment must read this retained program. Exact ablation removes only the
   retained option and restores the frozen primitive deployment.

The ARC environment remains the external behavioural verifier; Lean checks the
shared finite selection-and-promotion contract over the observations emitted by
that verifier. This does not place ARC execution inside the Lean kernel.

## Fixed bounds and controls

- Deployment budget: 120 actions.
- Discovery: at most 512 episodes, primitive depth 32, 3000 training actions,
  and 3 levels.
- Coordinate grounding: stride 8, at most 256 grounded actions.
- Cold baseline: frozen cyclic primitive deployment.
- Sham: first executed zero-progress training candidate with a fresh replay.
- Failed replay: exact selected tag under a recomputed constant quotient.
- Exact ablation: remove the retained option while preserving the primitive
  alphabet and deployment bound.

## Acceptance boundary

A positive result requires matching initial-state hashes; a discovered option;
a fresh pre-promotion replay that strictly exceeds the cold level count; exact
selection and promotion by the shared Lean implementation; retention of the
same program digest; fresh warm improvement; sham refusal; and ablation failure.
Any mismatch, missing candidate, Lean rejection, timeout, or unsupported action
interface is reported as verifier-inconclusive or failure, never as success.

This is selection and retention within a bounded action-program language. It is
not grammar genesis and does not establish broad ARC-3 generalization.
